# Live Monitor Portfolio

A static-first Next.js frontend plus a Cloudflare Worker backend for managing and showcasing real deployed websites as live iframe portfolio cards.

## Local Development

One command for the full local app:

```bash
npm ci
npm run dev:all
```

This starts both local services in one terminal:

- Frontend: `http://localhost:3000`
- Worker API: `http://localhost:8787`

`dev:all` also defaults the frontend API base to `http://localhost:8787`, so the homepage calls the local Worker proxy for `/public-good`.

Frontend only:

```bash
npm run dev
```

Manual full local flow, if you want separate terminals:

```bash
copy .env.example .env.local
cd worker
npm install
copy .dev.vars.example .dev.vars
npm run dev
```

In another terminal from the repository root:

```bash
npm run dev
```

To verify the public-good Worker proxy directly:

```bash
curl http://localhost:8787/public-good
```

The response should contain `success: true`, five `items`, `sourceApi: "https://api.isoyu.com/gy/api.php"`, and `cacheTtlSeconds: 21600`.

### Local public-good API behavior

The public-good module first tries the real upstream API:

```text
https://api.isoyu.com/gy/api.php
```

That endpoint can return a Cloudflare challenge page to local server-side requests. When that happens on `localhost`, the Worker returns the documented API sample first, then fills the rest of the five-person notice with safe fallback items. In that state the response has `isFallback: true` and a message that mentions local verification. This confirms the Worker route and frontend notice wiring without pretending the blocked upstream returned live data.

For stricter local verification, put a compact API response or an array of API responses into `worker/.dev.vars` and restart `npm run dev:all`:

```bash
PUBLIC_GOOD_FIXTURE_JSON='[{"success":true,"data":{"id":"448061","name":"李瑾怡","sex":"女","birth_time":"2004年02月17日","lost_time":"2020年01月01日","child_pic":"https://assets.example.com/child.jpg","lost_place":"湖北省荆州市监利县容城镇","url":"https://example.com/detail","child_feature":"圆脸，短发，走失时穿黄色外套。"},"contacts":{"consult_mail":"baobeihuijia@yeah.net","tel":"0435-3338090"},"name":"姬长信API","api":"https://api.isoyu.com/"}]'
```

If the fixture contains five valid unique records, `/public-good` returns them with `isFallback: false` and does not call the third-party API.

## Environment Variables

Frontend `.env.local`:

- `NEXT_PUBLIC_API_BASE_URL`
- `NEXT_PUBLIC_UPTIMEFLARE_API_URL`

Worker secrets:

- `ADMIN_PASSWORD`
- `SESSION_SECRET`

For local `wrangler dev`, put these in `worker/.dev.vars` or `worker/.env`.
Remote `wrangler secret put ...` values are not enough for local development.

## D1 Setup

Run these yourself when you're ready to bind real local and remote data:

```bash
cd worker
npx wrangler d1 create live-monitor-portfolio
```

Copy the returned `database_id` into `worker/wrangler.toml`, then run:

```bash
cd worker
npx wrangler secret put ADMIN_PASSWORD
npx wrangler secret put SESSION_SECRET
npx wrangler d1 migrations apply live-monitor-portfolio --local
```

For local Worker auth to work, also create:

```bash
cd worker
copy .dev.vars.example .dev.vars
```

Then edit `worker/.dev.vars` and set the same local password you want to use in `/admin`.

If you want to seed the default demo site after logging into `/admin`, you can call:

```bash
curl -X POST http://127.0.0.1:8787/sites/seed
```

The seed endpoint requires a valid admin session cookie, so in practice you should first log in from the browser-based `/admin` page, or seed manually by inserting your own sites through the admin form.

## Deployment

- `Cloudflare Pages` serves the static frontend generated by `next build`
- `Cloudflare Worker` handles auth and site CRUD
- GitHub Actions workflows live in `.github/workflows/`

Cloudflare-specific resources like D1 creation, secret injection, and dashboard credentials should be configured outside the repo.
